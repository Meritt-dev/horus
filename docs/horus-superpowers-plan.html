Planning note

Horus Superpowers Plan

A lightweight backlog for capabilities that amplify Horus's existing deterministic investigation engine instead of creating parallel command paths or duplicate providers.

Architecture Guardrail

Evidence always wins. AI may explain evidence, but it must not create evidence. Every item below should extend the canonical owner already present in the codebase.

Priority 1: Trace Connector

Goal

Turn distributed traces into first-class Horus evidence so investigations can follow a request across services, queues, databases, and source symbols.

Current repo reality: traces are already modeled as an evidence gap, and evidence can carry links.traceId, but there is no real tracing connector and no connect tracing route.

Connector Sources

Mode Data source What Horus can know
Native traces OpenTelemetry, Jaeger, Tempo, Honeycomb, Datadog, New Relic, cloud tracing Span tree, timing, service boundaries, errors, attributes, trace IDs
Trace-like reconstruction Logs with request IDs, correlation IDs, job IDs, traceparent headers Best-effort request path with explicit confidence limits
Zero-code telemetry eBPF/proxy/service-mesh tools such as Beyla, Pixie, Hubble, Envoy, Istio Network/service spans, HTTP status, latency, dependency edges
Bootstrap instrumentation Generated OTel setup for Node, Python, Go, Java, Ruby, .NET Future trace data after the user adds instrumentation

First Slice

  1. Add a canonical trace provider contract in packages/connectors.
  2. Ingest spans as deterministic evidence, preserving trace/span IDs and source system.
  3. Teach the engine to clear or downgrade the existing traces gap.
  4. Render trace paths in the report and packet without changing investigation ownership.
  5. Add source-symbol enrichment only when span attributes or route names can be matched safely.
